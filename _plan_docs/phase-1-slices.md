# Diligo — Phase 1 execution, sliced vertically

`plan.md` says *what* was decided. This is *how* it gets built: cut into vertical
slices rather than horizontal layers — each slice is a thin, complete path through
every layer it needs (Next.js → FastAPI → Rust/HF inference → Convex, as applicable),
demoable end-to-end, rather than "finish the whole backend, then the whole frontend."
That's also what makes the parallel-build decision in `plan.md` work in practice: the
ML engineer and the shell team meet at the API contract inside *each* slice, not once
at the very end.

Scoped to Phase 1 only (cap table reconciliation, the 6-8 week window, the 3-pilot
rollout) — branding/naming/tech-stack choices are already decided and applied; what's
left to slice is the build itself. Phase 2/3 are sketched at the bottom, not sliced —
per the plan, their scope is deliberately deferred until Phase 1's outcome data exists.

Each slice lists what makes it real, not theoretical: the thing you can actually click,
upload, or watch happen when it's done.

## Slice 1 — Walking skeleton

**Goal**: prove all four services are deployed and can talk to each other, with zero
real business logic yet.
**Ships when**: a founder can open the Next.js app, hit a button, and see a round trip
through FastAPI → the Rust inference service on Hugging Face Inference Endpoints → back
to the screen — even if the payload is a placeholder. Convex and auth are wired in as
empty scaffolding (a logged-in session exists; it doesn't gate anything real yet).
**Touches**: Next.js/Vercel, FastAPI/Railway, Rust/candle on HF, Convex, auth skeleton.
**Why first**: this is where the API contract between the ML pipeline and the shell
gets pinned down — the thing the parallel-build decision depends on.

## Slice 2 — Single-document ingestion → raw extraction

**Goal**: attack the highest-risk item first — the Rust pipeline's unfinished
generative path (multimodal splicing, tokenizer/chat-template handling) — before
anything else is built on top of it.
**Ships when**: a founder uploads one real cap table PDF and sees the raw
extracted text come back in the UI. No structuring, no math, no attorney — just proof
the finished pipeline reads a real document correctly.
**Touches**: Next.js upload UI, FastAPI ingestion endpoint, Rust/HF inference.
**Risk flag**: if this slice runs long, it's the earliest possible warning that the
6-8 week timeline is in danger — surface that immediately rather than discovering it
in week 6.

## Slice 3 — Structured field extraction

**Goal**: turn raw extracted text into the actual fields reconciliation math needs
(share counts, security type, dates, dollar amounts, party names).
**Ships when**: the same single-document upload now renders as a structured table,
not raw text — visibly parsed, not just OCR'd.
**Touches**: FastAPI (owns the parsing/characterization logic, per the tech-stack
decision), Rust/HF inference output as input.

## Slice 4 — Multi-document reconciliation

**Goal**: the actual core value — cross-reference a cap table against its SAFEs,
notes, and option pool, and surface where the numbers don't agree.
**Ships when**: a founder uploads a cap table *and* its supporting SAFEs/notes
together, and sees a findings list of concrete discrepancies (e.g. "cap table shows
14.2% option pool; SAFEs imply 15.8%") — still raw AI output, no attorney yet.
**Touches**: FastAPI (reconciliation math, entirely backend-owned).
**Maps to**: the Phase 1 wedge itself — this slice *is* "cap table reconciliation."

## Slice 5 — Attorney review loop

**Goal**: make the trust model real. Nothing a founder sees as a final report was
generated by AI alone.
**Ships when**: Slice 4's findings route into a Convex-backed review queue; a
contracted attorney logs in, sees the queue, and can approve, edit, or reject each
finding; a founder only ever sees the attorney-approved version of the report.
**Touches**: Convex (live queue/dashboard state — its actual job per the tech-stack
decision), FastAPI (serves findings to the queue), auth (now doing real work — attorney
and founder are different roles with different views).
**Maps to**: the full in-app attorney dashboard decision, and the AI + human sign-off
trust model from Idea.

## Slice 6 — Accounts and billing

**Goal**: turn the product into something that can actually be sold.
**Ships when**: a founder can create an account, subscribe (Dodo Payments,
subscription tier), and unlock a one-time attorney-signed report (Dodo Payments,
event-fee tier) — the hybrid pricing model, live.
**Touches**: Next.js (account/billing UI), FastAPI or Convex (whichever owns
subscription state — resolve this concretely in-slice; it's the same open item flagged
in `plan.md`'s tech stack section), Dodo Payments (`@dodopayments/nextjs` +
Python SDK).
**Sequencing note**: this can build in parallel with Slice 5 rather than after it —
billing doesn't depend on the review loop being finished, only on accounts existing.

## Slice 7 — India pilot rollout (100X.VC + Sequoia Surge)

**Goal**: real usage, not a demo.
**Ships when**: founders from both India pilot programs are onboarded, uploading real
documents, and getting real attorney-reviewed findings from the contracted Indian
attorney. This is where the Phase 1 exit criterion starts accumulating — attorney-
confirmed real errors caught, tracked from here.
**Touches**: everything above, plus the actual pilot relationships and the contracted
attorney being live.
**Maps to**: staggered-by-jurisdiction rollout, India pair first.

## Slice 8 — Hub71 / UAE pilot rollout

**Goal**: extend to the second jurisdiction once the first is proven.
**Ships when**: Hub71 founders are onboarded, with the separate DIFC/ADGM-qualified
attorney relationship live and reviewing findings.
**Gate**: per the plan, this doesn't start until Slice 7 has produced real signal —
don't pull it forward just because the engineering is ready early.
